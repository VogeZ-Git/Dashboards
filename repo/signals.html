The z column is optimistic and should not be read as a p-value. The forward windows of nearby signals overlap heavily, so the effective sample is far smaller than the signal count. Treat |z| under about 2 as nothing, and treat a larger value as "worth a proper test", not as a result.

This is still in-sample. These are the same signals under the same settings that were chosen on this data. It cannot tell you a model works. It can tell you a model has stopped working, which is the failure this system was otherwise blind to - compare the 90-day row against the all-history row.

The 90-day row lags reality by one forward horizon. A +20-bar score needs 20 bars to elapse first, so on a daily model the most recent month of signals contributes nothing here, and the window really covers about two months rather than three. The amber line under the toolbar states the dates actually measured. Treat this tab as a slow instrument, not a current one.

All six models moving together is a regime, not six discoveries. If every row's sell side turns strong in the same quarter, the tape fell - that is what the window-matched baseline exists to subtract, and if a signal survives it in only one model it is worth more than the same number in all six.

Median, not mean. One 300% move should not be able to rescue a model, and with this many small samples it otherwise would.

WHAT THIS IS

Every trigger from all six model pages in one list, newest first, with read state. It exists so the TradingView alerts do not have to be watched as they arrive - the same signals are here afterwards, and they stay here.

Nothing is computed on this page. It merges the sig_*.json files the six builds write, so it is exactly as current as the last build of each source. The header shows the age of each one, and a source that has not built recently is called out at the top rather than looking quiet.

THE INBOX

One row per signal. The model chips filter by source, the window buttons by age, and a click on any row marks it read. MARK ALL READ sets a watermark at the newest signal currently in view, so the normal routine is: open, read what is highlighted, mark all read, close.

+5 / +20 BARS is what the price did after the signal, coloured in the signal's own direction - green means the signal was right. Recent signals have no value there yet. Read the two summary tiles for the base rate before acting on any single row.

THE MATRIX

Every ticker against every model: the current state, and how long ago that model last fired. A shaded cell fired inside the highlight window.

AGREEMENT ONLY keeps the tickers where at least two different models fired in the same direction inside the window. That is the closest thing here to a confluence signal - and it is worth being clear that it is a heuristic, not a tested one. The models share the same price series, so they are not independent witnesses.

THE HEALTH TAB

Every model measured against the thing that makes a hit rate meaningful: what the same tickers did anyway over the same window. For each signal the forward move is scored in the signal's own direction, then compared with that ticker's unconditional distribution over the identical period.

MEDIAN MOVEMedian forward move after these signals, in the signal's direction. Positive = the signals were followed by the move they implied.
BASELINEThe same statistic for every bar in those tickers, signals or not. This is what you would have got by entering at random.
EXCESSThe column that matters. Median of the per-signal difference. Zero means the model told you nothing you would not have got by throwing a dart at the same names.
HIT % / BASELINE % / HIT EDGEThe same comparison on frequency rather than size. A model can be right more often and still lose money, so read this next to EXCESS, not instead of it.
zHow many standard errors the hit edge sits from zero, computed as if the signals were independent. They are not - see the caveat on the tab.

The use of it is the comparison between windows. A model with a healthy all-history excess and a negative 90-day one has stopped working, and that is the single thing this system could not tell you before.

HOLDINGS

When the holdings handler is deployed, every signal row shows the value of the position you hold in that name and HELD ONLY cuts the list to things you can actually act on. Positions held in names no model watches are listed next to the read-state note - those are the blind spots, and they do not appear anywhere else.

Positions come from the brokerage sheets, so they are as current as those sheets are. Nothing here places or checks an order.

READ STATE

Read state lives in the same Apps Script web app that serves the live prices, so marking a signal read on the phone marks it read on the desktop. Every change is written to this browser first and pushed afterwards, so the page still works with the sync endpoint down - the note next to the buttons says which is in effect. If the endpoint has not been extended with the state handler yet, this page falls back to browser-local state and keeps working.

WHAT THIS PAGE IS NOT

It is a recomputed history, not a record of alerts you received. Each build recalculates the signals from the current price data and the current settings. Change a preset, and this page's version of the past changes with it. Signals that used to exist and no longer do are kept in the archive and shown struck through under the ARCHIVE toggle on each model's own page.

Six models on 39 tickers generate a lot of rows. Something has fired somewhere on almost any given day. The point of the read state and the windows is to stop that volume from being a reason to look at all of it - not to imply that every row deserves a trade.

None of these models has a demonstrated out-of-sample edge on this watchlist. That is documented on each model's own page and is not softened by collecting them here. Use this to see what is stretched or turning, then decide on your own thesis.
